# OryxOS 需求分析

## 1. 产品定义

OryxOS 是可部署在企业自有基础设施中的 Agent 运行与管理底座。它让团队使用目录和 Markdown 定义 Agent，并复用统一的模型、工具、Skill、知识、记忆、渠道、调度、安全和审计能力。

## 2. 目标用户与问题

| 用户 | 主要问题 | 期望结果 |
|---|---|---|
| 平台管理员 | Agent 分散部署，模型密钥、权限、版本和日志难统一 | 在一个管理面配置、审计和运维多个 Agent |
| Agent 开发者 | 每个 Agent 都重复实现模型调用、工具循环、记忆和 API | 只定义 Agent 和业务工具即可交付 |
| 业务系统开发者 | 不希望理解 Agent 内部实现 | 通过稳定 REST API 调用 Agent |
| 安全与合规人员 | Agent 能执行命令、读文件、访问外网，风险不可见 | 最小权限、完整审计、高风险动作可控 |
| 最终用户 | 希望从 CLI、Web 或 IM 使用同一业务能力 | 跨渠道获得一致、可追踪的结果 |

## 3. 目标与非目标

### 目标

- 一个实例可运行多个相互独立的 Agent。
- Agent 可在不改 Java 代码的情况下定义或更新。
- 模型、工具、记忆、知识、渠道和调度可复用。
- 工具执行受白名单和审计约束。
- 能从单机试点演进到企业共享部署。

### 当前非目标

- 不自研基础模型。
- 不用可视化工作流替代所有确定性业务流程。
- 不承诺所有路线图能力已经生产可用。
- 不允许 Agent 绕过企业现有授权直接获得业务系统权限。

## 4. 核心使用场景

### 场景 A：企业知识支持

员工从 Web 或 IM 提问，Agent 检索被授权知识库，回复时携带引用；检索不到或置信不足时转人工。

验收重点：权限隔离、引用准确、无答案时不编造、查询全程可审计。

### 场景 B：受控运维

Agent 读取告警和运行手册，先执行只读诊断；涉及变更时生成操作计划并等待审批，批准后执行并记录结果。

验收重点：只读与写操作分权、审批、超时、失败回滚和命令审计。

### 场景 C：流程工单

Agent 判断工单类型、补齐信息、查询业务系统并提出处理建议；满足规则后执行，例外情况转人工。

验收重点：身份映射、幂等、状态一致性、人工接管和处理时限。

## 5. 功能需求

### FR-1 Agent 生命周期

- 使用 `.oryxos/agents/<name>/AGENT.md` 定义 Agent。
- 支持创建、查看、更新、归档和热加载。
- 每个 Agent 可独立绑定 Provider、Tool、Skill、知识库和调度。

### FR-2 模型路由

- Provider 与 Agent 解耦，支持运行时增删改查。
- 支持 OpenAI 兼容服务和本地推理服务。
- 调用失败必须返回明确错误并写入审计；后续可扩展降级和成本路由。

### FR-3 执行循环

- 模型可请求工具，系统负责校验、执行并把结果返回模型。
- 必须限制最大迭代次数、超时和输出大小。
- 每一步应携带 Session、Agent 和调用追踪标识。

### FR-4 Tool、Skill 与 MCP

- 提供基础文件、Shell 和 HTTP 工具。
- 支持按 Agent 限定工具集合。
- 支持 Markdown Skill、MCP Server 和原生 Java Tool。
- 工具失败不得被静默吞掉。

### FR-5 Memory 与 Knowledge

- 区分会话历史、长期记忆和知识库。
- 长期记忆按 Agent 隔离；知识检索结果必须可引用。
- 支持关键词与向量检索组合，并允许替换后端。

### FR-6 渠道与通知

- CLI、REST 和 Web 管理台提供基础入口。
- 消息渠道统一转换为内部消息模型。
- 通知渠道按名称配置，密钥不写入 Agent 文档。

### FR-7 调度

- 支持 Cron、时区、启停、立即执行和执行历史。
- 同一计划在多副本环境中不得重复执行。

### FR-8 安全与审计

- 文件路径、Shell 命令、HTTP 域名采用默认拒绝、显式放行。
- 工具调用和 LLM 调用持久化记录。
- 对外部署必须启用认证授权；高风险操作需要审批能力。

### FR-9 管理与 API

- 提供 Agent、Provider、渠道、Session、Schedule、Tool、Sandbox 和 Workspace 管理接口。
- API 使用统一响应结构和明确错误码。
- 管理台不得成为绕过后端权限校验的特殊入口。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 密钥不入库明文或代码仓库；默认最小权限；管理 API 开启认证后才能暴露到非可信网络 |
| 可靠性 | Session 与审计写入失败时可感知；调度幂等；重启后状态可恢复 |
| 可观测性 | 健康检查、结构化日志、Prometheus/OTLP 指标和跨模块 trace id |
| 性能 | 阻塞 I/O 使用虚拟线程；并发与模型限流可配置；工具和模型调用设置超时 |
| 可维护性 | 模块职责清楚；新增渠道或 Tool 不修改核心循环；数据库变更走迁移脚本 |
| 可移植性 | 支持 Linux、容器和 K8s；开发使用 SQLite，集群使用 PostgreSQL 与共享工作区 |

## 7. 优先级

### P0：可安全使用的单机底座

Agent 生命周期、Provider、ReAct、Tool、Memory、Knowledge、REST、管理台、调度、通知、白名单和审计。

### P1：企业共享部署

PostgreSQL、共享工作区、多副本调度、认证授权、密钥管理、备份恢复和资源限额。

### P2：高级协作

Flow、子 Agent、A2A、人机审批、成本治理、模型智能路由和多租户。

## 8. 验收标准

1. 新建 Agent 后无需重启即可通过 REST 发起一次会话并调用受允许工具。
2. 未授权文件、命令和域名访问被拒绝，并产生可查询审计记录。
3. Agent A 无法读取 Agent B 的长期记忆和未绑定知识库。
4. 调度任务按指定时区执行，禁用后不再触发，执行历史可查询。
5. 重启服务后 Agent、Session、Schedule 和审计记录可恢复。
6. Provider 或 Tool 故障时，调用返回可定位的错误，不伪装成成功。
7. 管理 API 在开启认证后拒绝无凭证访问。

## 9. 主要风险

- Agent 的非确定性可能造成重复或越权动作，需要幂等键、审批和限制。
- Prompt Injection 可通过知识或网页内容诱导工具调用，必须让数据和指令分层。
- 白名单是应用级防线，不等于容器或主机级强隔离。
- 多副本下数据库一致不代表文件工作区一致，共享存储需要单独验证。
- 能力快速扩张会增加攻击面，新增渠道和 Tool 必须带威胁建模与测试。
