# OryxOS 编程指南

## 1. 环境准备

要求：Git、Java 21、Maven 3.9+。管理台由 Maven 构建自动准备 Node.js，常规后端构建无需单独安装全局 Node。

```bash
git clone https://github.com/oryx-labs/oryxos.git
cd oryxos
mvn package -DskipTests
```

也可直接使用官方容器镜像进行功能体验：

```bash
docker run -d --name oryxos -p 8080:8080 \
  -v oryxos-data:/data ghcr.io/oryx-labs/oryxos:latest
curl http://localhost:8080/api/v1/health
```

默认 SQLite 只运行一个容器；多副本必须使用 PostgreSQL 和共享工作区。

## 2. 本地启动

```bash
cp config/application.yml.example config/application.yml
# 在本地配置文件或环境变量中设置一个 Provider；不要提交密钥
bin/start.sh
```

默认入口：

- 健康检查：`http://localhost:8080/api/v1/health`
- 管理台：`http://localhost:8080/admin/`
- OpenAPI：`http://localhost:8080/swagger-ui`

停止服务：

```bash
bin/stop.sh
```

## 3. 先理解主链路

修改代码前先沿真实调用链阅读：

```text
外部消息
→ Channel/Controller
→ Agent + Session
→ PromptBuilder
→ ProviderService
→ ReActLoop
→ ToolExecutor/SandboxChecker
→ Tool result
→ Audit + Session persistence
→ 回复
```

Bug 修复应优先改所有调用方共享的根因位置，不在每个 Controller 或 Channel 重复打补丁。

## 4. 常见开发任务

### 4.1 新增 Agent

优先通过管理台、REST API 或现有 CLI 创建，不需要新增 Java 类。最小结构：

```text
.oryxos/agents/my-agent/
└── AGENT.md
```

只有在需要新的执行能力时才新增 Tool；仅需操作说明或知识时使用 Skill/Knowledge。

### 4.2 新增 Tool

按成本从低到高选择：

1. 复用已有内置 Tool。
2. 编写 `SKILL.md` 指导 Agent 组合现有工具。
3. 接入现成 MCP Server。
4. 用任意语言实现自有 MCP Server。
5. 只有深度 Java 集成或性能要求明确时，才新增原生 `@Tool`。

Tool 必须定义清楚名称、参数 Schema、错误语义、超时和权限要求；返回内容保持小而结构化。

### 4.3 新增 Channel

在 `channels/` 下按现有模块复制最相近的最小结构，实现统一入站消息转换和出站回复。认证、签名、重试、限流放在 Channel 边界；不要把平台 SDK 类型泄漏进 `oryxos-core`。

### 4.4 新增 Provider

先确认 OpenAI 兼容配置是否已经覆盖。确需新实现时，通过 `oryxos-provider` 的显式名称映射接入，不使用不透明的类型扫描。密钥解析与模型创建分开，配置变更后使缓存安全失效。

### 4.5 数据库变更

只增加 Flyway migration，不手改已有 migration。SQLite 和 PostgreSQL 都要验证；SQL 方言不同的部分必须明确隔离。

## 5. 代码约束

- 使用 Java 21 和现有 Spring/Maven 体系，不为一个小功能增加新框架。
- `oryxos-core` 不依赖具体 Channel、数据库或厂商 SDK。
- Agent 配置不保存明文密钥。
- 外部输入在 Controller、Channel、Tool 和 MCP 边界校验。
- Tool 执行必须经过统一 Sandbox 和审计链路。
- 异常转成明确错误，不返回伪成功，不记录敏感数据。
- 新功能复用现有接口和模块；不为单一实现创建工厂或抽象层。
- 路线图功能不提前留空壳，真实需求出现时再增加。

## 6. 测试

最小检查：

```bash
mvn test
```

提交前完整检查以仓库现有 Maven profile 和 CI 为准。针对改动至少留下一个能在回归时失败的测试：

| 改动 | 最小有效测试 |
|---|---|
| ReAct 分支或循环 | 工具调用一次、最终回复、达到上限三个关键路径中的相关路径 |
| Sandbox | 一个允许案例和一个绕过/拒绝案例 |
| Provider | 名称路由、错误映射或配置刷新 |
| Repository | 临时数据库集成测试与 migration |
| REST API | 成功响应和一个边界错误 |
| Channel | 入站转换或签名校验 |

不要只验证“正常输入能跑”，安全和持久化改动必须覆盖失败路径。

## 7. 使用 AI 编程

### 提示词应包含

- 要解决的真实问题和可复现步骤；
- 预期行为与当前行为；
- 涉及模块和不能破坏的约束；
- 验收命令；
- 要求先查现有实现和全部调用方。

示例：

```text
修复 Schedule 在多副本下可能重复执行的问题。
先查找 Schedule 的创建、抢占、执行和持久化完整调用链，说明根因后再改。
复用现有 Repository 和数据库约束，不新增中间件。
补一个最小并发集成测试，并运行相关 Maven 模块测试。
```

### 评审 AI 产出

1. Diff 是否只改了问题需要的文件。
2. 是否复用了现有能力而不是新增重复工具类。
3. 是否把症状修在入口而共享根因仍存在。
4. 是否引入密钥泄露、越权、SSRF、路径穿越或命令注入。
5. 测试是否能在回退修复后失败。
6. 文档是否把规划能力写成已实现。

## 8. Git 与 PR

```bash
git switch -c fix/short-description
git status --short
git diff --check
mvn test
git add <明确的文件>
git commit -m "fix: describe the root cause"
git push -u origin fix/short-description
```

PR 应说明：问题、根因、最小修复、验证证据和风险。不要混入格式化全仓库、无关重构或生成文件。

## 9. 完成定义

- 需求和边界明确；
- 实现位于正确的共享层；
- 相关测试通过；
- 安全和失败路径已检查；
- 配置、数据库或 API 变化已更新文档；
- Diff 无无关改动，且可由维护者复现验证。
