# OryxOS 技术方案

## 1. 设计原则

1. 单机先完整，分布式按真实需求演进。
2. 一个目录定义一个 Agent，运行能力由底座复用。
3. Agent 只获得显式绑定的 Tool、Skill、Knowledge 和 Channel。
4. 模型只提出工具请求，应用负责校验和执行。
5. 审计、安全和失败处理属于主链路，不是后补插件。
6. 优先使用 Spring、Maven、数据库迁移和标准协议，减少自定义基础设施。

## 2. 技术栈

| 层 | 选择 |
|---|---|
| 运行时 | Java 21、Spring Boot |
| 模型抽象 | Spring AI；应用保留 ReAct 和 Tool 执行控制权 |
| 构建 | Maven 多模块 |
| 管理台 | Vue 3 + Vite，构建后随服务静态发布 |
| 本地存储 | SQLite + 文件工作区 |
| 集群存储 | PostgreSQL + 共享 POSIX 工作区 |
| 数据迁移 | Flyway |
| CLI | Picocli |
| 扩展协议 | MCP、REST/OpenAPI、Markdown Skill、Java `@Tool` |
| 可观测性 | 结构化日志、Micrometer、Prometheus、OTLP |

## 4. 模块职责

| 模块 | 职责 |
|---|---|
| `oryxos-core` | Agent、Session、ReAct、Prompt、调度与核心接口 |
| `oryxos-provider` | Provider 注册、模型构建、显式名称路由 |
| `oryxos-tool` | 内置 Tool、MCP、注册表、执行器和 Sandbox 检查 |
| `oryxos-memory` | 长期记忆、保存与召回 |
| `oryxos-knowledge` | 文档切分、索引、混合检索和引用 |
| `oryxos-persona` | 内置和自定义 Persona |
| `oryxos-storage` | SQLite/PostgreSQL、Repository 和数据库迁移 |
| `oryxos-web` | REST Controller、统一错误、认证及管理台资源 |
| `oryxos-cli` | 初始化、聊天、服务和管理命令 |
| `channels/*` | CLI 与各消息平台适配器 |
| `oryxos-boot` | Spring Boot 入口、配置和模块聚合 |

边界原则：新增 Channel 或 Tool 通过扩展模块和注册机制接入，不修改 ReAct 核心流程。

## 5. 核心流程

### 5.1 消息处理

1. Channel 或 REST 将外部消息转成统一请求。
2. 系统解析 Agent，创建或恢复 Session。
3. `ContextLoader` 加载 Agent 指令、Persona、记忆、已绑定 Skill 元数据和知识上下文。
4. `PromptBuilder` 生成模型输入，`ProviderService` 选择模型。
5. 若模型返回工具请求，`ToolExecutor` 先执行授权、参数、超时和 Sandbox 校验。
6. 执行结果写入审计并回填会话，继续下一轮。
7. 达到最终回复、最大轮数、超时或错误后结束，并经原 Channel 返回。

### 5.2 Agent 定义

```text
.oryxos/agents/ops-agent/
├── AGENT.md
├── MEMORY.md
├── REFERENCE.md
├── scripts/
└── skills/        # 指向共享 Skill 的绑定
```

`AGENT.md` 的 frontmatter 只保存运行配置和引用，不保存明文密钥；正文保存任务边界和行为说明。单机模式监听工作区变化，集群模式通过管理 API 写入并由版本轮询协调。

### 5.3 记忆与知识

- Session 保存完整对话与状态。
- Memory 保存 Agent 跨会话事实和偏好，按 Agent 隔离。
- Knowledge 是可独立管理的资料集合，经切分、索引后混合检索。
- 检索采用关键词、向量及必要的时间权重融合；回答保留来源引用。
- 嵌入服务不可用时允许降级到关键词检索，但必须暴露降级状态。

## 6. 数据设计

关系数据至少包含：Agent 元数据、Provider、通知渠道、Session、Message、Schedule、Schedule Execution、Tool Invocation、LLM Call、Sandbox Rule 和 Workspace Version。

关键约束：

- Agent 名称、Provider 名称和调度业务键唯一。
- Tool Invocation 与 LLM Call 关联 Session、Agent 和 trace id。
- 密钥字段只保存密文或外部密钥引用。
- 调度执行使用唯一执行键防止多副本重复。
- 数据库模式变更只能通过 Flyway。

## 7. 安全方案

### 控制面

- 管理 API 与普通调用 API 分权。
- 对外部署必须启用认证；角色至少区分管理员、开发者、调用者和审计员。
- Provider 密钥从环境变量、密钥服务或加密存储解析，不进入 Git 和日志。

### 执行面

- 文件、Shell、HTTP 默认拒绝，按 Agent 和环境授权。
- 规范化路径后再判断白名单，防止 `..`、符号链接和编码绕过。
- Shell 使用参数化执行或严格命令策略，限制时间、工作目录、环境变量和输出。
- HTTP 防止访问环回、元数据地址和未授权内网，处理 DNS 重绑定和重定向。
- 高风险写操作增加人机审批；生产环境优先使用容器或远程隔离后端。

### Prompt Injection

网页、知识库和工具结果都视为不可信数据。系统指令、用户请求与检索内容分层；任何外部内容都不能自行扩大工具权限。

## 8. 部署方案

### 单机

- 一个 OryxOS 进程；SQLite；本地 `.oryxos/` 工作区。
- 适合开发、评审和单部门试点。
- 容器使用持久卷保存配置、数据库、工作区和日志。

### 集群

- 多个无状态应用副本；PostgreSQL；共享 POSIX 工作区。
- 调度抢占、Workspace Version 和幂等键处理并发。
- Ingress、TLS、密钥服务、集中日志和指标由企业平台提供。

注意：共享数据库只能解决关系状态一致性；文件锁、原子替换、缓存失效和跨节点可见性仍需独立验证。

## 9. 可观测性

- 指标：模型/工具成功率、耗时、Token、成本、ReAct 轮数、调度延迟、队列和资源使用。
- 日志：结构化输出，包含 trace id、session id、agent name 和 tool name，不记录密钥和敏感正文。
- Trace：一次用户请求贯穿 Channel、Session、LLM、Tool 和通知。
- 审计：与运行日志分离，支持筛选、导出、留存和权限控制。

## 10. 验证策略

1. 单元测试覆盖权限校验、路径规范化、Provider 路由、迭代上限和错误映射。
2. 集成测试使用临时 SQLite/PostgreSQL 验证迁移、Repository 和调度幂等。
3. 合约测试验证 REST 响应和 Channel 消息转换。
4. 安全测试覆盖路径穿越、SSRF、命令绕过、密钥泄露和 Prompt Injection。
5. 端到端测试至少覆盖知识支持、受控运维和流程工单三个场景。

## 11. 演进顺序

```text
单机安全闭环
  → PostgreSQL + 共享工作区
  → 认证授权 + 审批 + 成本治理
  → Flow / 子 Agent / A2A
  → 多租户与规模化运营
```

每一阶段都以可测的生产问题为触发条件，不为未来场景提前引入新中间件。
