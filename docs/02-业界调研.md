# OryxOS 业界调研

## 1. 调研问题

本调研回答四个问题：Agent 产品目前分成哪些层次；企业真正需要什么；OryxOS 处于哪一层；它的机会与风险是什么。

## 2. Agent 技术栈分层

业界产品边界正在交叉，但仍可按主要交付物分为四类：

| 层次 | 主要交付物 | 代表 | 优势 | 使用方仍需负责 |
|---|---|---|---|---|
| 模型与工具调用框架 | SDK、API、Agent loop 组件 | Spring AI、LangGraph | 灵活、可编程、适合深度定制 | 部署、权限、渠道、运维和治理 |
| 多 Agent/流程框架 | 图、Flow、Crew | LangGraph、CrewAI | 状态化流程、委派和可控编排 | 生产平台和企业集成 |
| AI 应用平台 | 可视化工作流、RAG、应用发布 | Dify | 低代码、交付快、面向应用 | 深层运行时控制与特定企业治理 |
| 自主 Agent/Agent OS | 常驻 Agent、工具、记忆、渠道、调度 | Hermes Agent、OryxOS | 开箱即用的完整执行环境 | 场景配置、工具接入和治理策略 |

Spring AI 官方将 Tool Calling 定义为 Agent 系统的基础构件，并同时支持由框架驱动或应用自行驱动工具循环；LangGraph 以图表达状态化、多步骤、多角色流程；Dify 聚焦可视化工作流、RAG 和应用发布。这说明“框架—平台—运行底座”并不是同一层产品。

## 3. 企业需求

企业的核心诉求不是拥有一个新的技术名词，而是让 Agent 在生产环境中可控地执行：

1. **数据边界明确**：支持私有部署和本地模型，敏感数据不离开批准的基础设施。
2. **权限最小化**：每个 Agent 只获得完成任务所需的模型、工具、文件、命令和网络权限。
3. **全过程可追溯**：记录输入、模型调用、工具调用、结果、耗时、成本和操作者。
4. **能够接入现有系统**：ERP、CRM、工单、知识库、监控和身份系统不能成为孤岛。
5. **可运营**：能查看健康状态、失败率、延迟、成本、任务历史和 Agent 版本。
6. **风险操作有人控制**：高风险工具需要审批、暂停、回滚或人工接管。

模型能力会快速变化，因此企业底座的长期价值更可能来自稳定的执行边界、集成资产、知识沉淀和治理数据。

## 4. OryxOS 的市场位置

OryxOS 当前定位为自托管的企业 Agent OS。它不是单纯的 Agent SDK，也不是以可视化流程为核心的应用平台。其当前产品形态包含：

- 一个目录定义一个 Agent；
- Provider 动态管理与模型路由；
- 自实现 ReAct 循环；
- Memory、Knowledge、Skill、MCP 和原生 Tool；
- CLI、REST API、Web 管理台、Cron、通知与消息渠道；
- 文件、命令和网络白名单；
- LLM 与工具调用审计；
- 单机 SQLite，以及面向 PostgreSQL、共享工作区和多副本的演进路径。

它的差异化假设是：大量企业后端和治理体系已经建立在 Java/Spring 上，因此 Java 原生底座可以减少跨语言运维、集成和审计成本。这是合理的市场切入点，但需要用真实部署数据证明，而不能只凭技术栈推导需求。

## 5. 竞争与互补关系

### 与 Hermes Agent

两者都能自托管并提供完整 Agent 运行环境。Hermes 在工具、多模态、个人生产力入口和执行后端方面覆盖更广；OryxOS 更集中于多 Agent 管理、Java 企业集成、管理 API 和审计。它们既竞争，也可互相借鉴。

### 与 Dify

Dify 的核心优势是可视化构建、RAG 和应用发布。OryxOS 的核心优势是 Agent 运行底座、目录化定义和执行治理。实际企业架构中，应用编排层可以调用 Agent OS 的 API，两者并不必然互斥。

### 与 Spring AI / LangGraph

这些是构建组件或框架。OryxOS 可以复用 Spring AI 的模型与工具协议能力，但需要自己负责 Agent 生命周期、管理面、持久化、渠道、安全和审计。框架更适合“写一个高度定制的 Agent”，OryxOS 试图解决“统一运行很多 Agent”。

## 6. SWOT 分析

| 类别 | 结论 |
|---|---|
| 优势 | Java/Spring 原生；单制品自托管；目录化 Agent；管理台、API、审计和沙箱能力集中 |
| 劣势 | 社区和生态体量仍小；部分企业治理及多 Agent 协作仍在路线图；Java AI 人才密度低于 Python |
| 机会 | 企业 Agent 从 Demo 进入治理阶段；MCP 降低工具接入成本；严监管行业需要本地、可审计底座 |
| 威胁 | 云厂商和现有 AI 平台向 Agent 管理层扩张；通用框架快速补齐生产能力；“Agent OS”品类边界尚未稳定 |

## 7. 建议

1. 优先把“企业可控”转化为可验收能力：RBAC、审批、审计查询、密钥托管和租户隔离。
2. 建立少而完整的标杆场景，例如知识支持、受控运维和流程工单，而不是只增加工具数量。
3. 发布与同类项目相同任务集的评测：完成率、人工接管率、成本、延迟和故障恢复。
4. 保持开放标准：MCP、OpenAPI、可替换 Provider 和可导出的 Agent/Skill 定义。
5. 将“当前实现、实验能力、路线图”持续分开，降低用户预期偏差。
